# Generic Mod Artifacts And CAT/DAT Deployment

Forge treats the selected mod project folder as the source of truth. The in-browser
`ModWorkspace` is an editable model and cache; it is not required to hold every file byte.
This distinction lets Forge edit very large and mixed-content mods without placing their
entire payload in browser memory.

## Ownership

Every regular source file receives one build disposition:

- `generated`: a Forge compiler/emitter claims the path and its generated bytes replace the source path;
- `source-copy`: no emitter claims the path, so Forge copies its bytes from disk without interpreting them;
- `excluded`: development metadata or a project exclusion, reported but never shipped;
- `runtime-owned`: mutable deployed state that a validated deployment preserves;
- error: an unsafe path, symlink/reparse point, case-fold collision, missing source, or changed hash.

Unknown names and extensions default to `source-copy`. There are no rules for particular mods or
hardcoded payload filenames.

Universal exclusions are `.git/**`, `.hg/**`, `.svn/**`, `.claude/**`, `.kilo/**`, `.forge/**`,
`.forge-builds/**`, `.snapshots/**`, `.studio-mod-id`, `.forgekeep`, `node_modules/**`, and
`.forgeartifact.json`.

## Project Rules

An optional `.forgeartifact.json` at the mod root adds glob rules:

```json
{
  "exclude": ["private/**", "working-notes/**"],
  "runtimeOwned": ["runtime/**", "state/*.db"],
  "catalogLoose": ["preview.*", "external-loader/**"]
}
```

- `exclude` removes source-only material from artifacts.
- `runtimeOwned` omits mutable source placeholders and preserves the matching deployed path during replacement.
- `catalogLoose` includes the file but leaves it loose at the extension root instead of putting it in CAT/DAT.

All matched rules appear in the deploy artifact report. A preserved path that conflicts with a newly
built file stops deployment instead of guessing which owner wins.

## Build And Deploy

Staging builds are complete, hash-verified loose artifacts under
`<Mod Workspace>/.forge-builds/loose/<modId>`; they never replace the source checkout. Explicit game deployment builds a separate
scratch artifact first, keeps `content.xml`, configured `catalogLoose` files, and pre-existing root
catalog parts loose, and streams all other payload into deterministic `ext_XX.cat/.dat` volumes.

Forge then reopens every catalog through its reader, verifies paths, sizes, offsets, MD5, SHA-256, and
aggregate DAT lengths. Only a verified artifact is moved into the extension directory. Replacement uses
a sibling stage and backup: declared runtime state is copied into the stage, the old folder is renamed,
the new folder is activated and re-verified, and a failed activation restores the old folder.

Deploy API responses include an `artifact` report with source/generated file counts, bytes, exclusions,
runtime-owned paths, output-file count, catalog-volume count, and `verified` status.

## Size Limits

The 256 KiB per-file and 6 MiB aggregate thresholds remain only as browser-import memory protection.
They mark large files as tracked-but-not-inlined. They are not compiler or deployment limits: the disk
artifact planner hashes and streams those files directly. If a tracked large file has no available disk
source, compilation fails closed and asks for a re-import instead of silently omitting it.

## Directory Roles

- **Mod Workspace Folder**: the editable development/source area. Generic create/write/delete API calls target this root.
- **Filesystem Folder**: a read/browse/import view, normally the installed game's `extensions` directory.
- **X4 Game Installation**: supplies the explicit deploy target at `<game>/extensions`.

Generic filesystem writes never select the installed extensions folder merely because it is configured.
Only the explicit validated deploy operation owns game-directory replacement.
